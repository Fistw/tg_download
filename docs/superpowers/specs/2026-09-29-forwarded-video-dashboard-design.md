# 转发视频任务前端展示设计

**日期：** 2026-09-29

**状态：** 已批准并实现

## 目标

在 React 管理看板的“下载历史”页展示 Bot 收到的转发视频下载任务。用户可以看到每批任务的当前进度、失败数量和最终状态；任务记录在服务重启后仍可查询。

## 方案

每条单独转发的视频是一批，每个 Telegram 相册是一批。后端在现有 `MonitoringDB` SQLite 数据库中新增批次记录表，保存批次类型、聊天和发送者标识、视频总数、已下载数、失败数、状态及创建/更新时间。记录与视频文件分离，数据库记录失败时不阻断 Telegram 下载。

Bot 开始处理一批视频前创建 `downloading` 记录；每条视频下载完成或失败后更新计数。批次结束后标记为 `completed`、`partially_failed` 或 `failed`。服务启动时将遗留的 `downloading` 批次标为 `interrupted`，保留已记录的计数，不自动重试。

`MonitoringApp` 增加受现有会话认证保护的只读批次 API。React“下载历史”页按当前 10 秒轮询周期调用该 API，在现有文件级下载记录之外显示一个批次列表。每批显示任务类型、开始时间、已下载数/总数、失败数和状态。记录沿用监控数据库 7 天保留期。旧版静态看板不在本次范围内。

## 组件与数据流

1. `bot_handler.py` 创建并更新一个批次记录；批次内仍按顺序处理视频，不同批次可并行。
2. `monitoring_db.py` 管理批次表、计数更新、查询、7 天清理及重启恢复标记。
3. `webdav_server.py` 提供已认证的批次查询 API。
4. React 下载历史页通过 `web/src/api/client.ts` 读取批次数据并定时刷新。

API 返回最近 7 天的批次，按创建时间倒序，限制最多 100 条。前端为活动、完成、部分失败、失败和中断状态提供清楚的文字标签。

## 错误处理

- SQLite 初始化或更新批次记录失败时写日志，Bot 仍继续下载并更新 Telegram 状态消息。
- API 查询失败时保留当前页面数据并沿用已有错误处理方式。
- 服务重启导致未完成批次中断时保留批次及其进度；用户可在前端看出它没有完成。
- 访问批次 API 继续使用看板已有的 Cookie 登录认证。

## 验收方式

- 单条转发作为 1/1 批次显示，并从进行中变为完成。
- 相册按视频项总数显示进度；有失败项时显示部分失败及失败数量。
- 多个批次在页面上分别显示，互不覆盖进度。
- 服务重启后，完成记录仍显示，未完成记录显示为中断。
- 未登录会话不能读取批次 API。

## 不在范围内

- 展示每个视频的独立行、取消或重试任务。
- Telegram 文件字节级进度条。
- 旧版静态看板的改造。
